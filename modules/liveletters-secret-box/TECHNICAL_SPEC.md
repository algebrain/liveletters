# liveletters-secret-box

## Назначение

`liveletters-secret-box` это криптографическая утилита локального уровня LiveLetters. Она отвечает за один конкретный механизм: превращение открытого секрета (пароля почтовой учётки) в формат `obf:v1:<base64>`, который можно безопасно хранить в SQLite, и обратное восстановление по локальному файлу ключа.

## Зона ответственности

- XChaCha20-Poly1305 encrypt/decrypt одного секрета за раз;
- хранение 32-байтного ключа в отдельном файле `mail-password-obfuscation.key`;
- генерация ключа при первом запуске через `OsRng`;
- выставление прав 0o600 на ключевой файл на Unix;
- проверка целостности Poly1305-tag и формата токена при расшифровке;
- ленивое различение обфусцированного и открытого значения по префиксу `obf:v1:`.

## Что модуль не должен делать

- знать про SQLite, схемы, миграции, materialized state;
- зависеть от `liveletters-store` или `liveletters-config`;
- хранить больше одного секрета за раз;
- выступать в роли менеджера паролей;
- делать ротацию ключей;
- защищать секрет от атакующего, уже работающего от имени того же пользователя.

## Почему выбран XChaCha20-Poly1305

- AEAD с быстрым, простым и хорошо изученным примитивом.
- 192-битный nonce позволяет генерировать его через `OsRng` без риска коллизий, в отличие от 96-битных nonce в ChaCha20-Poly1305.
- Poly1305 даёт встроенную аутентификацию, поэтому любая подмена ciphertext даст `SecretBoxError::Crypto` при расшифровке.
- Не требует nonce-management на стороне caller: каждый вызов `obfuscate` генерирует свежий nonce, кладёт его первыми 24 байтами payload и зашифровывает остаток.

## Структура payload

`obfuscate` возвращает строку формата:

```
obf:v1:<base64(nonce || ciphertext)>
```

где:

- `obf:v1:` — префикс-маркер формата (4 ASCII-символа `obf:`, 2 символа версии `v1:`, итого 6 байт);
- `nonce` — 24 байта, сгенерированных через `OsRng`;
- `ciphertext` — XChaCha20-Poly1305(`plaintext`), длина `len(plaintext) + 16` байт (16 байт — Poly1305-tag);
- base64 — стандартный алфавит с паддингом `=`.

`deobfuscate` зеркально проверяет префикс, декодирует base64, проверяет, что длина строго больше 24 байт, отрезает nonce, расшифровывает AEAD и проверяет, что результат — валидный UTF-8.

## Файл ключа

Имя файла: `mail-password-obfuscation.key`.

Расположение: внутри `data_dir` (по умолчанию `~/.local/share/liveletters/data` или эквивалент через `StorePaths`).

Содержимое: ровно 32 байта.

Права:

- при создании на Unix выставляются 0o600 через `std::os::unix::fs::PermissionsExt`;
- на других платформах `0o600` пропускается (поведение `ensure_key` не зависит от платформы для существующих файлов).

## Два конструктора: open vs open_or_create

Решение о разделении API на `open` и `open_or_create` — намеренное.

- `open` — для сценариев, где ключ уже должен быть на диске. Никогда не генерирует ключ.
- `open_or_create` — для сценариев first-run, тестов, восстановления после потери. Генерирует ключ, только если файла нет.

Это страховка от двух классов ошибок:

1. caller случайно «создаёт» сейф в обычном runtime-пути и затирает существующий ключ новым случайным значением — после этого все ранее сохранённые токены в БД становятся нерасшифровываемыми;
2. caller в first-run-пути случайно «открывает» сейф и получает невнятный `Io`-error вместо нормальной генерации ключа.

Разделение даёт статическую (через имя метода) гарантию того, что именно произойдёт.

## Формат ошибок

`SecretBoxError`:

- `Io { source, message }` — проблема файловой системы. `source` отдаёт исходную `std::io::Error`.
- `InvalidKeyLength { path, expected, actual }` — файл ключа существует, но длина не 32 байта. Это защита от подмены ключа чем-то посторонним.
- `InvalidFormat { message }` — токен не парсится: нет префикса, плохой base64, короткий payload, не UTF-8.
- `Crypto { message }` — сбой AEAD: неверный ключ, испорченный ciphertext, подделанный Poly1305-tag.

`SecretBoxError` намеренно **не различает** «неверный ключ» и «испорченный токен» во внешнем сообщении: оба возвращают `Crypto { message: "decryption failed: …" }`. Это закрывает оракул-канал, через который атакующий мог бы перебирать ключи по-битово, наблюдая за разными типами ошибок.

## Текущее минимальное состояние реализации

Сейчас модуль уже включает:

- `SecretBox` с двумя конструкторами `open` и `open_or_create`;
- методы `obfuscate` / `deobfuscate` / `is_obfuscated` / `key_path`;
- `default_key_path(data_dir)` для расчёта канонического пути к ключу;
- `SecretBoxError` с четырьмя вариантами и реализованным `From<std::io::Error>`;
- 9 integration-тестов в `tests/codec.rs`: round-trip, уникальность nonce, отказ на чужом ключе, проверка префикса, отказ на не-обфусцированном входе, на битом base64, на укороченном payload, на отсутствующем файле ключа, на ключе с неверной длиной.

## Требования к структуре каталога

- `src/lib.rs`;
- `src/codec.rs`;
- `src/error.rs`;
- `src/key_file.rs`;
- `tests/codec.rs`.

Все файлы `src/` ≤ 64 строк. Этот лимит соблюдается.

## Требования к тестам

Покрытие тестами обязательно.

Реализованные проверки:

- round-trip одного и того же plaintext через одного и того же сейфа;
- различие токенов для одного plaintext за счёт случайного nonce;
- невозможность расшифровки токена сейфом, открытым по другому ключу;
- корректность предиката `is_obfuscated` на положительных и отрицательных примерах;
- отказ `deobfuscate` на строках без префикса `obf:v1:`;
- отказ `deobfuscate` на битом base64;
- отказ `deobfuscate` на укороченном payload;
- отказ `open` на отсутствующем файле ключа;
- отказ `open` на файле ключа неверной длины.

## Требования к документации

Обязательна документация:

- описание формата токена `obf:v1:<base64>`;
- описание разделения `open` vs `open_or_create`;
- описание файла ключа и его прав;
- описание вариантов `SecretBoxError` и причин их возникновения;
- явная фиксация того, что модуль не делает (ротация ключей, защита от keylogger и т. п.).

## Критерии готовности

- `SecretBox` корректно шифрует и расшифровывает строки;
- `is_obfuscated` отличает обфусцированные значения от открытых;
- файл ключа создаётся с 0o600 на Unix;
- `open` никогда не генерирует ключ;
- `open_or_create` никогда не затирает существующий ключ;
- 9 integration-тестов зелёные.

Сейчас практически считаются уже закрытыми:

- генерация ключа через `OsRng`;
- AEAD на XChaCha20-Poly1305;
- интеграция с `liveletters-store::secret_bridge` и `StorePaths::password_obfuscation_key_path`;
- покрытие тестами всех перечисленных выше сценариев отказа.

Модуль пока не считается завершенным в части:

- нет отдельного API для явной ротации ключей;
- нет инструмента для миграции токенов со старого ключа на новый;
- нет проверки, что файл ключа не шире 32 байт (текущая проверка ловит только неверные длины, но не учитывает будущие версии формата файла).

Эти направления зафиксированы как следующий шаг, но не блокируют текущую версию.
