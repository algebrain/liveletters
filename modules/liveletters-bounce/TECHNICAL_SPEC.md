# `liveletters-bounce` TECHNICAL_SPEC

## Назначение

`liveletters-bounce` распознаёт автоматические почтовые уведомления о недоставке и извлекает из них минимальные данные, нужные LiveLetters.

Основной сценарий: пользователь отправил запрос подписки, почтовый сервер вернул уведомление о невозможности доставки, а синхронизация должна сопоставить это уведомление с записью в исходящей очереди.

## Зона ответственности

- определить, является ли сырое письмо уведомлением о доставке;
- отличить уведомление о доставке от обычного письма и жалобы на спам;
- извлечь действие доставки, статус, конечного получателя, диагностический код и исходный `Message-ID`;
- вернуть `Ok(None)` для писем, которые не являются уведомлениями о доставке.

## Что крейт не должен делать

- не читает почту с сервера;
- не отправляет письма;
- не разбирает протокольные сообщения LiveLetters;
- не открывает базу и не меняет состояние подписок;
- не решает, как именно отображать отказ пользователю.

## Модель данных

```rust
pub struct BounceReport {
    pub action: BounceAction,
    pub status: String,
    pub final_recipient: String,
    pub diagnostic_code: String,
    pub original_message_id: Option<String>,
}

pub enum BounceAction {
    Failed,
    Delayed,
    Delivered,
    Relayed,
    Expanded,
    Other(String),
}
```

`BounceReport` хранит только поля, которые сейчас нужны для синхронизации и диагностики. Полный исходный текст письма в структуру не переносится.

## Алгоритм разбора

`parse_dsn(raw_email)` работает в несколько шагов:

1. ищет заголовок `Content-Type`;
2. проверяет, что это `multipart/report` с `report-type=delivery-status`;
3. ищет в теле поля `Action`, `Status`, `Final-Recipient`, `Diagnostic-Code`;
4. ищет `Original-Message-ID`;
5. если отдельного `Original-Message-ID` нет, пытается найти `Message-ID` во вложенной секции `message/rfc822`;
6. возвращает `Some(BounceReport)` для уведомления о доставке или `None` для прочих писем.

Отсутствие заголовка `Content-Type` считается ошибкой `BounceError::MissingHeader`, потому что без него нельзя надёжно отличить уведомление о доставке от обычного письма.

## Границы реализации

Разбор сделан узким и практичным:

- поддерживается стандартная форма `multipart/report; report-type=delivery-status`;
- жалобы на спам с `report-type=feedback` не считаются уведомлениями о доставке;
- значения полей ищутся как строки вида `Name: value`;
- сложные вложенные варианты MIME пока не нормализуются полностью.

Если понадобится поддержка новых форматов уведомлений, её нужно добавлять через новые тестовые письма в `tests/dsn_parse.rs`.

## Зависимости

- `liveletters-log` — для совместимости с общим слоем журналирования;
- `thiserror` — тип ошибки `BounceError`.

Крейт не зависит от почтового транспорта, хранилища или движка синхронизации.

## Тесты

`tests/dsn_parse.rs` проверяет:

- разбор стандартного уведомления о недоставке;
- игнорирование жалобы на спам;
- игнорирование обычного письма.

Тесты проверяют именно поведение разбора, а не наличие имён в коде.
