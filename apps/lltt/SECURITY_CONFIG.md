# Настройки безопасности `config.toml`

`lltt` хранит защитные квоты и лимиты в per-user-файле
`users/<имя>/config.toml` внутри домашнего каталога LiveLetters. Эти
настройки защищают локальную базу и почтовый канал от перегрузки при
аномальном всплеске входящих писем, а не управляют повседневным
поведением блога. Документ описывает каждый параметр: что он ограничивает,
какое значение `lltt` использует по умолчанию, когда его стоит менять и к
каким последствиям это приведёт.

## Где находится файл и как создаётся

Полный путь для пользователя `alice`:

```
$LIVELETTERS_HOME/users/alice/config.toml
```

Если `LIVELETTERS_HOME` не задан — это `~/.liveletters/users/alice/config.toml`.
Файл лежит рядом с per-user-базой `lltt.db`, которую `lltt` открывает при
выполнении команд от имени этого пользователя.

Файл создаётся **один раз**, при первом `lltt user add <имя>`, и заполняется
кодовыми значениями по умолчанию. При последующих вызовах он не
перезаписывается. Если файл удалить, `lltt` снова работает на кодовых
значениях — при следующем `user add --force` или вручную файл можно
восстановить.

## Режим «переопределение», а не полная замена

Файл не обязан содержать все ключи. Каждый параметр имеет собственное
кодовое значение: отсутствующий ключ заменяется им, заданный — применяется.
Поэтому минимальный рабочий файл может переопределять один лимит:

```toml
schema_version = 1

[ingest_limits]
max_deferred_total = 5
```

Остальные лимиты останутся кодовыми. Это удобно для экспериментов: не нужно
копировать весь canonical-файл, достаточно указать изменившиеся значения.

Неизвестные `lltt` поля в файле игнорируются ( совместимость с будущими
версиями), но лучше их не добавлять, чтобы не вводить в заблуждение.

## Доступ к файлу

Файл **не управляется** командой `lltt settings` и намеренно не описан в
[`TUTORIAL.md`](TUTORIAL.md). Это низкоуровневая настройка для
сопровождающего сборку или опытного пользователя, который понимает
последствия. Правка выполняется вручную в любом текстовом редакторе:

```sh
nano "$LIVELETTERS_HOME/users/alice/config.toml"
```

Изменения вступают в силу при следующем запуске команды `lltt` (никакой
перезагрузки демона нет: `lltt` перечитывает файл при каждом запуске sync
или импорта).

## Когда файл вообще трогать не нужно

Для подавляющего большинства пользователей кодовые значения подходят как
есть. Менять их стоит только если:

- вы наблюдаете конкретную проблему (база раздувается, sync долго
  выполняется, провайдер почты жалуется на объём исходящих);
- вы понимаете, какой именно лимит ограничивает нормальную или,
  наоборот, атакующую нагрузку;
- вы готовы наблюдать за поведением после изменения.

Без причины менять значения не нужно — это не ускорит `lltt` и не сделает
его «безопаснее».

## Раздел `[mime_limits]`

Лимиты MIME-разбора письма. Применяются **до** того, как `lltt` начнёт
работать с содержанием письма: слишком большие или структурно сложные
письма отклоняются как `malformed`, не доходя до базы событий. Эти лимиты
действуют и при импорте `.eml` через `lltt inbox import`, и при `lltt sync
pull`.

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `max_raw_email_bytes` | `10485760` (10 МБ) | Максимальный размер сырого письма целиком |
| `max_human_bytes` | `1048576` (1 МБ) | Максимальный размер человекочитаемой `text/plain`-части |
| `max_json_bytes` | `1048576` (1 МБ) | Максимальный размер вложения `liveletters.json` |
| `max_parts` | `8` | Максимальное число MIME-частей в письме |
| `max_depth` | `2` | Максимальная глубина вложенности `multipart` |

### Когда менять

- **Письма журнального размера.** Если вы ведёте длинный текстовый блог и
  ваши записи законно превышают 1 МБ текста, поднимите `max_human_bytes`.
  Помните: 1 МБ текста — это большой лонгрид; возможно, лучше разбить
  запись на части.
- **Строгая почтовая гигиена.** Если ваш провайдер режет вложения или вы
  хотите жёстче отсекать мусор до разбора, опустите `max_raw_email_bytes`
  (например, до 1 МБ). Это уменьшит трафик при `sync pull`, но легитимные
  большие письма начнут попадать в `malformed`.

### Последствия

- Увеличение `max_*` поднимает потолок расхода памяти, диска и времени
  разбора на одно письмо. Злонамеренно огромное письмо сможет стоить `lltt`
  дороже, поэтому значения должны оставаться разумными.
- Уменьшение `max_parts`/`max_depth` безопасно: протокол v1 всё равно
  требует ровно одну `text/plain` и один `liveletters.json` (см.
  [протокол v1](../../docs/protocol-v1.md)). Дополнительно ограничивать
  структуру обычно не требуется.

## Раздел `[ingest_limits]`

Квоты на один цикл приёма писем — один вызов `lltt sync pull`, `lltt sync
backfill` или один `lltt inbox import`. Считаются в памяти на время батча и
не накапливаются между запусками. Превышение квоты отклоняет событие с
исходом `rate_limited` (см. [диагностику ниже](#диагностика)), не применяя
его.

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `max_deferred_total` | `100` | Максимум отложенных событий после батча |
| `max_deferred_per_origin` | `10` | Из них — от одного `origin` |
| `max_new_authors_per_batch` | `50` | Максимум ранее неизвестных авторов за батч |
| `max_auto_responses_per_batch` | `20` | Максимум сформированных `subscription_confirmed` за батч |
| `max_events_per_origin` | `50` | Максимум событий от одного `origin.email` |
| `max_events_per_source` | `50` | Максимум событий от одного `source.email` |

`origin` — первичный автор события, `source` — непосредственный отправитель
(владелец ресурса при пересылке). Подробное объяснение полей — в
[протоколе v1](../../docs/protocol-v1.md).

### `max_deferred_total` и `max_deferred_per_origin`

Отложенные события (`deferred_events`) возникают, когда комментарий пришёл
раньше записи, подтверждение — раньше запроса и т. п. Без потолка серия
комментариев к несуществующему посту способна линейно раздувать очередь.

- `max_deferred_total` — жёсткий потолок размера очереди после батча. При
  достижении новые «откладываемые» события отклоняются как `rate_limited` с
  причиной `deferred_total_quota_exceeded`.
- `max_deferred_per_origin` — защита от одного источника, засоряющего
  очередь. Причина отказа — `deferred_per_origin_quota_exceeded`.

**Когда менять.** Если у вас медленный или часто отстающий транспорт и
легитимно копится много отложенных событий, потолок можно поднять.
Снижать стоит, если вы видите, что очередь забивается спамом и хотите
быстрее его отсекать. Помните: при `reprocess_deferred` (переобработка)
квоты отключены, поэтому легитимные зависимости доразрешатся позже.

### `max_new_authors_per_batch`

Каждое письмо с ранее не встречавшимся `origin` добавляет запись в таблицу
`authors`. Без потолка атакующий способен за один pull создать тысячи
мусорных авторов, замедлив поиск и засорив интерфейс. Причина отказа —
`new_authors_quota_exceeded`.

**Когда менять.** Поднимите, если вы разово импортируете большой архив
переписки с множеством реальных авторов (например, мигрируете с другой
системы). Снижать ниже 50 не рекомендуется: обычная волна подписок или
обсуждений может привести несколько десятков новых авторов за один sync.

### `max_auto_responses_per_batch`

При получении `subscription_requested` владелец ресурса автоматически
отвечает `subscription_confirmed`. Без потолка один атакующий pull с
десятками поддельных запросов способен заставить ваш SMTP рассылать
десятки писем на произвольные адреса — это вредит репутации вашего ящика и
может привести к блокировке провайдером. Причина отказа —
`auto_response_quota_exceeded`.

Важно: при превышении **подписка всё равно сохраняется** в локальном
состоянии владельца (она не порождает трафик сама по себе). Подавляется
только исходящее письмо-уведомление. Подписчик может повторить запрос
позже, и тогда квота восстановится.

**Когда менять.** Поднимите, если у вас ожидается массовая легитимная
волна подписок (например, анонс блога) и вы готовы отправить много
уведомлений за один раз — но сверьтесь с лимитами вашего SMTP-провайдера.
Снижайте, если провайдер жестко ограничивает исходящий объём и вы хотите
перестраховаться.

### `max_events_per_origin` и `max_events_per_source`

Ограничивают, сколько событий от одного отправителя обрабатывается за
батч. Защищает от сценария, когда один `origin` шлёт поток постов или
комментариев. Причины отказа — `events_per_origin_quota_exceeded` и
`events_per_source_quota_exceeded`.

**Когда менять.** Поднимите для `backfill`-сценария с большим архивом от
одного автора. Снижение помогает жёстче отсекать флуд, но рискует
задеть активное обсуждение, где один автор оставляет много комментариев.

## Раздел `[retention]`

Политика удержания сырых писем (`raw_messages`). В отличие от
`ingest_limits`, действует **между** запусками — это регулярная чистка
мусора, которую `lltt sync pull` выполняет в конце цикла.

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `raw_messages_ttl_days` | `14` | Сколько суток хранить «мусорные» сырые письма |
| `raw_messages_max_kept` | `5000` | Верхняя граница числа «мусорных» сырых писем |

«Мусорными» считаются статусы `malformed`, `invalid` и `rate_limited`.
Легитимная история (`applied`, `duplicate`, `bounce.applied`) чисткой не
затрагивается.

- `raw_messages_ttl_days` — удаляются записи старше N суток. Слишком малое
  значение лишит вас диагностической трассы при разборе инцидента; слишком
  большое — будет копить мусор.
- `raw_messages_max_kept` — если мусорных записей больше N, удаляются самые
  старые. Полезно при внезапном всплеске: даже за один pull чистка не даст
  базе разрастись сверх предела.

**Когда менять.** На tight-disk-сервере опустите оба. Для длительной
диагностики поднимите `raw_messages_ttl_days`. На практике 14 суток и 5000
записей покрывают и диагностические нужды, и защиту от роста.

## Диагностика

Срабатывание квот видно в нескольких местах:

- **Отчёт `lltt sync pull`** содержит строку:
  ```text
  лимиты:               12
  ```
  Это число событий, отклонённых как `rate_limited` в текущем батче.
- **`lltt inbox list --status rate_limited`** показывает конкретные
  сырые письма, попавшие в квоту. Команда `lltt inbox show <message-id>`
  раскрывает полное тело для разбора причины.
- **Журнал** (если включён через `lltt set log.level info`) содержит строки
  вида `sync.ingest outcome=rate_limited ... reason=...` с точной причиной.

Причины и их смысл перечислены в таблицах выше (`*_quota_exceeded`).

## Полный пример (значения по умолчанию)

Так выглядит файл сразу после `lltt user add`:

```toml
schema_version = 1

[ingest_limits]
max_auto_responses_per_batch = 20
max_deferred_per_origin = 10
max_deferred_total = 100
max_events_per_origin = 50
max_events_per_source = 50
max_new_authors_per_batch = 50

[mime_limits]
max_depth = 2
max_human_bytes = 1048576
max_json_bytes = 1048576
max_parts = 8
max_raw_email_bytes = 10485760

[retention]
raw_messages_max_kept = 5000
raw_messages_ttl_days = 14
```

## Примеры частичного переопределения

Зажать лавину отложенных событий строже, не трогая остальное:

```toml
schema_version = 1

[ingest_limits]
max_deferred_total = 30
max_deferred_per_origin = 3
```

Дать простор для массовой волны легитимных подписок (внимание к лимитам
вашего SMTP-провайдера):

```toml
schema_version = 1

[ingest_limits]
max_auto_responses_per_batch = 100
max_new_authors_per_batch = 200
```

Снизить трафик при sync на медленном канале, отсекая большие письма раньше:

```toml
schema_version = 1

[mime_limits]
max_raw_email_bytes = 1048576
max_human_bytes = 262144
```

## Чего делать не следует

- **Не удаляйте секцию целиком, если не уверены.** Удалённая подсекция
  возвращается к кодовым значениям — это безопасно, но может удивить, если
  вы рассчитывали на свои числа.
- **Не правьте через `lltt settings set`.** Этот канал управления не
  затрагивает `config.toml`; лимиты нельзя менять через `lltt set`.
- **Не делайте значения нулевыми или отрицательными.** Ноль означает
  «запретить всё»: каждый батч будет полностью отклоняться. Это сломает
  sync, не дав ничего полезного.
- **Не храните секреты в этом файле.** Пароли и ключи лежат в
  `mail_settings` и файле обфускации; `config.toml` — для квот, не для
  секретов.
