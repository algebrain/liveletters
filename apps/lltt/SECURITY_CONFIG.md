# Настройки безопасности `config.toml`

`lltt` хранит защитные квоты и лимиты в отдельном для каждого пользователя
файле `users/<имя>/config.toml` внутри домашнего каталога LiveLetters. Эти
настройки защищают локальную базу и почтовый канал от перегрузки при
аномальном всплеске входящих писем, а не управляют повседневным поведением
блога. Документ описывает каждый параметр: что он ограничивает, какое
значение `lltt` использует по умолчанию, когда его стоит менять и к каким
последствиям это приведёт.

## Где находится файл и как создаётся

Полный путь для пользователя `alice`:

```
$LIVELETTERS_HOME/users/alice/config.toml
```

Если переменная `LIVELETTERS_HOME` не задана — это
`~/.liveletters/users/alice/config.toml`. Файл лежит рядом с отдельной
базой пользователя `lltt.db`, которую `lltt` открывает при выполнении
команд от его имени.

Файл создаётся **один раз**, при первом `lltt user add <имя>`, и
заполняется кодовыми значениями по умолчанию. При последующих вызовах он
не перезаписывается. Если файл удалить, `lltt` снова работает на кодовых
значениях; восстановить файл можно повторным `user add --force` или вручную.

## Режим переопределения, а не полная замена

Файл не обязан содержать все ключи. Каждый параметр имеет собственное
кодовое значение: отсутствующий ключ заменяется им, заданный — применяется.
Поэтому минимальный рабочий файл может переопределять один лимит:

```toml
schema_version = 1

[ingest_limits]
max_deferred_total = 5
```

Остальные лимиты останутся кодовыми. Это удобно для экспериментов: не
нужно копировать файл целиком, достаточно указать изменившиеся значения.

Неизвестные `lltt` поля в файле игнорируются (для совместимости с
будущими версиями), но лучше их не добавлять, чтобы не вводить в
заблуждение.

## Доступ к файлу

Файл **не управляется** командой `lltt settings` и намеренно не описан в
[`TUTORIAL.md`](TUTORIAL.md). Это низкоуровневая настройка для
сопровождающего сборку или опытного пользователя, который понимает
последствия. Правка выполняется вручную в любом текстовом редакторе:

```sh
nano "$LIVELETTERS_HOME/users/alice/config.toml"
```

Изменения вступают в силу при следующем запуске команды `lltt` (никакой
перезагрузки службы нет: `lltt` перечитывает файл при каждом запуске
синхронизации или импорта письма).

## Когда файл вообще трогать не нужно

Для подавляющего большинства пользователей кодовые значения подходят как
есть. Менять их стоит только если:

- вы наблюдаете конкретную проблему (база раздувается, синхронизация
  долго выполняется, провайдер почты жалуется на объём исходящих);
- вы понимаете, какой именно лимит ограничивает нормальную или,
  наоборот, недобросовестную нагрузку;
- вы готовы наблюдать за поведением после изменения.

Без причины менять значения не нужно — это не ускорит `lltt` и не сделает
его «безопаснее».

## Два термина, которые встретятся ниже

В событиях LiveLetters есть два поля, связанных с отправителем. Они
важны для понимания квот:

- **первичный автор события** — поле `origin`. Для поста или комментария
  это автор текста;
- **непосредственный отправитель** — поле `source`. Заполняется, когда
  письмо пересылает не автор события, а владелец ресурса (например,
  комментарий Алисы Боб пересылает своим подписчикам).

Полное описание этих полей — в [протоколе v1](../../docs/protocol-v1.md).

## Раздел `[mime_limits]`

Лимиты разбора письма. Применяются **до** того, как `lltt` начнёт
работать с содержанием письма: слишком большие или структурно сложные
письма отклоняются как `malformed`, не доходя до базы событий. Эти лимиты
действуют и при импорте файла `.eml` через `lltt inbox import`, и при
получении писем через `lltt sync pull`.

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `max_raw_email_bytes` | `10485760` (10 МБ) | Наибольший размер сырого письма целиком |
| `max_human_bytes` | `1048576` (1 МБ) | Наибольший размер человекочитаемой части `text/plain` |
| `max_json_bytes` | `1048576` (1 МБ) | Наибольший размер вложения `liveletters.json` |
| `max_parts` | `8` | Наибольшее число частей в письме |
| `max_depth` | `2` | Наибольшая глубина вложенности составных частей |

### Когда менять

- **Длинные текстовые записи.** Если вы ведёте длинный блог и ваши записи
  законно превышают 1 МБ текста, поднимите `max_human_bytes`. Учтите: 1 МБ
  текста — это очень большой лонгрид; возможно, запись лучше разбить на
  части.
- **Экономия трафика.** Если ваш провайдер режет вложения или вы хотите
  жёстче отсекать мусор до разбора, опустите `max_raw_email_bytes`
  (например, до 1 МБ). Это уменьшит трафик при получении писем, но
  легитимные большие письма начнут попадать в `malformed`.

### Последствия

- Увеличение лимитов поднимает потолок расхода памяти, диска и времени
  разбора на одно письмо. Намеренно огромное письмо сможет стоить `lltt`
  дороже, поэтому значения должны оставаться разумными.
- Уменьшение `max_parts` и `max_depth` безопасно: протокол v1 всё равно
  требует ровно одну часть `text/plain` и одно вложение
  `liveletters.json`. Дополнительно ограничивать структуру обычно не
  требуется.

## Раздел `[ingest_limits]`

Квоты на один цикл приёма писем — один вызов `lltt sync pull`,
`lltt sync backfill` или один `lltt inbox import`. Подсчитываются в памяти
на время пакета и не накапливаются между запусками. Превышение квоты
отклоняет событие с исходом `rate_limited`, не применяя его (см. раздел
[«Диагностика»](#диагностика)).

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `max_deferred_total` | `100` | Наибольшее число отложенных событий после пакета |
| `max_deferred_per_origin` | `10` | Из них — от одного первичного автора |
| `max_new_authors_per_batch` | `50` | Наибольшее число ранее неизвестных авторов за пакет |
| `max_auto_responses_per_batch` | `20` | Наибольшее число автоматических ответов `subscription_confirmed` за пакет |
| `max_events_per_origin` | `50` | Наибольшее число событий от одного автора |
| `max_events_per_source` | `50` | Наибольшее число событий от одного отправителя |

### `max_deferred_total` и `max_deferred_per_origin`

Отложенные события возникают, когда комментарий пришёл раньше записи,
подтверждение — раньше запроса и тому подобное. Без потолка серия
комментариев к несуществующему посту способна линейно раздувать очередь.

- `max_deferred_total` — жёсткий потолок размера очереди после пакета. При
  достижении новые откладываемые события отклоняются с причиной
  `deferred_total_quota_exceeded`.
- `max_deferred_per_origin` — защита от одного источника, засоряющего
  очередь. Причина отказа — `deferred_per_origin_quota_exceeded`.

**Когда менять.** Если у вас медленный или часто отстающий транспорт и
легитимно копится много отложенных событий, потолок можно поднять.
Снижать стоит, если вы видите, что очередь забивается спамом и хотите
быстрее его отсекать. Учтите: при переобработке отложенных событий квоты
отключены, поэтому legitимные зависимости доразрешатся позже.

**Последствия.** Слишком низкий `max_deferred_total` будет часто
отклонять события в активном блоге с большой очередью; слишком высокий
перестаёт защищать от засора.

### `max_new_authors_per_batch`

Каждое письмо с ранее не встречавшимся первичным автором добавляет запись
в таблицу `authors`. Без потолка недобросовестный отправитель способен за
один приём создать тысячи мусорных авторов, замедлив поиск и засорив
интерфейс. Причина отказа — `new_authors_quota_exceeded`.

**Когда менять.** Поднимите, если вы разово импортируете большой архив
переписки с множеством реальных авторов (например, мигрируете с другой
системы). Снижать ниже 50 не рекомендуется: обычная волна подписок или
обсуждений может привести несколько десятков новых авторов за одну
синхронизацию.

### `max_auto_responses_per_batch`

При получении запроса подписки владелец ресурса автоматически отвечает
подтверждением `subscription_confirmed`. Без потолка один недобросовестный
приём с десятками поддельных запросов способен заставить ваш сервер
отправки рассылать десятки писем на произвольные адреса — это вредит
репутации вашего ящика и может привести к блокировке провайдером.
Причина отказа — `auto_response_quota_exceeded`.

Важно: при превышении **подписка всё равно сохраняется** в локальном
состоянии владельца (она не порождает трафик сама по себе). Подавляется
только исходящее письмо-уведомление. Подписчик может повторить запрос
позже, и тогда квота восстановится.

**Когда менять.** Поднимите, если ожидается массовая легитимная волна
подписок (например, анонс блога) и вы готовы отправить много уведомлений
за один раз — но сверьтесь с лимитами вашего провайдера отправки.
Снижайте, если провайдер жёстко ограничивает исходящий объём и вы хотите
подстраховаться.

### `max_events_per_origin` и `max_events_per_source`

Ограничивают, сколько событий от одного отправителя обрабатывается за
пакет. Защищает от сценария, когда один автор шлёт поток постов или
комментариев. Причины отказа — `events_per_origin_quota_exceeded` и
`events_per_source_quota_exceeded`.

**Когда менять.** Поднимите для сценария с большим архивом от одного
автора (разовое подтягивание прошлого). Снижение помогает жёстче отсекать
поток, но рискует задеть активное обсуждение, где один автор оставляет
много комментариев.

## Раздел `[retention]`

Политика удержания сырых писем (`raw_messages`). В отличие от квот
приёма, действует **между** запусками — это регулярная чистка мусора,
которую `lltt sync pull` выполняет в конце цикла.

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `raw_messages_ttl_days` | `14` | Сколько суток хранить «мусорные» сырые письма |
| `raw_messages_max_kept` | `5000` | Верхняя граница числа «мусорных» сырых писем |

«Мусорными» считаются статусы `malformed`, `invalid` и `rate_limited`.
Легитимная история (`applied`, `duplicate`, `bounce.applied`) чисткой не
затрагивается.

- `raw_messages_ttl_days` — удаляются записи старше указанного числа
  суток. Слишком малое значение лишит вас диагностической трассы при
  разборе инцидента; слишком большое — будет копить мусор.
- `raw_messages_max_kept` — если мусорных записей больше указанного,
  удаляются самые старые. Полезно при внезапном всплеске: даже за один
  приём чистка не даст базе разрастись сверх предела.

**Когда менять.** На сервере с ограниченным диском опустите оба. Для
длительной диагностики поднимите `raw_messages_ttl_days`. На практике
14 суток и 5000 записей покрывают и диагностические нужды, и защиту от
роста.

## Диагностика

Срабатывание квот видно в нескольких местах:

- **Отчёт `lltt sync pull`** содержит строку:
  ```text
  лимиты:               12
  ```
  Это число событий, отклонённых как `rate_limited` в текущем пакете.
- **`lltt inbox list --status rate_limited`** показывает конкретные
  сырые письма, попавшие в квоту. Команда `lltt inbox show <message-id>`
  раскрывает полное тело для разбора причины.
- **Журнал** (если включён через `lltt set log.level info`) содержит
  строки вида `sync.ingest outcome=rate_limited ... reason=...` с точной
  причиной.

Причины и их смысл перечислены в таблицах выше (все оканчиваются на
`_quota_exceeded`).

## Полный пример (значения по умолчанию)

Так выглядит файл сразу после `lltt user add`:

```toml
schema_version = 1

[ingest_limits]
max_auto_responses_per_batch = 20
max_deferred_per_origin = 10
max_deferred_total = 100
max_events_per_origin = 50
max_events_per_source = 50
max_new_authors_per_batch = 50

[mime_limits]
max_depth = 2
max_human_bytes = 1048576
max_json_bytes = 1048576
max_parts = 8
max_raw_email_bytes = 10485760

[retention]
raw_messages_max_kept = 5000
raw_messages_ttl_days = 14
```

## Примеры частичного переопределения

Ограничить лавину отложенных событий строже, не трогая остальное:

```toml
schema_version = 1

[ingest_limits]
max_deferred_total = 30
max_deferred_per_origin = 3
```

Дать простор для массовой волны легитимных подписок (внимание к лимитам
вашего провайдера отправки):

```toml
schema_version = 1

[ingest_limits]
max_auto_responses_per_batch = 100
max_new_authors_per_batch = 200
```

Снизить трафик при синхронизации на медленном канале, отсекая большие
письма раньше:

```toml
schema_version = 1

[mime_limits]
max_raw_email_bytes = 1048576
max_human_bytes = 262144
```

## Чего делать не следует

- **Не удаляйте секцию целиком, если не уверены.** Удалённая подсекция
  возвращается к кодовым значениям — это безопасно, но может удивить,
  если вы рассчитывали на свои числа.
- **Не правьте через `lltt settings set`.** Этот канал управления не
  затрагивает `config.toml`; лимиты нельзя менять через `lltt set`.
- **Не делайте значения нулевыми или отрицательными.** Ноль означает
  «запретить всё»: каждый пакет будет полностью отклоняться. Это сломает
  синхронизацию, не дав ничего полезного.
- **Не храните секреты в этом файле.** Пароли и ключи лежат в настройках
  почты и файле обфускации; `config.toml` — для квот, не для секретов.
