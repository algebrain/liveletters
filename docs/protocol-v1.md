# Протокол LiveLetters v1

Документ описывает публичный формат обмена LiveLetters v1: какие части
обычного письма используются, как внутри письма лежит технический JSON
`liveletters.json`, какие события допустимы и как получатель должен их
обрабатывать.

Цель протокола — передавать события между независимыми установками
LiveLetters через обычную электронную почту. Письмо должно оставаться
читаемым человеком, но содержать строгую машинную часть для синхронизации.

## Слои

В протоколе есть три слоя.

| Слой | Что содержит |
|---|---|
| Почтовый транспорт | SMTP для отправки, IMAP для получения, сырой текст письма RFC 5322 |
| MIME-конверт | Заголовки письма, `multipart/mixed`, человекочитаемый `text/plain`, вложение `liveletters.json` |
| Протокольный JSON | `envelope`, `origin`, необязательный `source`, `payload` |

Почтовый транспорт доставляет письмо. MIME-конверт делает письмо пригодным
для почтовых клиентов. JSON-вложение несёт событие, которое применяет
LiveLetters.

## Используемые части письма

LiveLetters-письмо является обычным письмом RFC 5322. В v1 используются
следующие заголовки:

| Заголовок | Назначение |
|---|---|
| `From` | Почтовый отправитель письма |
| `To` | Почтовый получатель письма |
| `Subject` | Человекочитаемая тема |
| `X-LiveLetters-Protocol: v1` | Маркер письма LiveLetters v1 |
| `MIME-Version: 1.0` | Признак MIME-письма |
| `Content-Type: multipart/mixed; boundary="liveletters-boundary"` | Контейнер частей письма |

`Subject` может быть ASCII-строкой или RFC 2047 encoded-word для
не-ASCII текста.

Заголовок `X-LiveLetters-Protocol: v1` используется для поиска писем
LiveLetters в почтовом ящике. Если IMAP-сервер не умеет искать по этому
заголовку, клиент может скачать заголовки или всё письмо и проверить
заголовок локально.

## MIME-структура

Каноническая форма исходящего письма:

```text
From: alice@example.org
To: bob@example.org
Subject: =?utf-8?B?...?=
X-LiveLetters-Protocol: v1
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="liveletters-boundary"

--liveletters-boundary
Content-Type: text/plain; charset="utf-8"

<человекочитаемый текст>
--liveletters-boundary
Content-Type: application/json; name="liveletters.json"
Content-Disposition: attachment; filename="liveletters.json"

<JSON-сообщение LiveLetters>
--liveletters-boundary--
```

Обязательные части:

- `text/plain; charset="utf-8"` — человекочитаемый текст письма;
- `application/json` с именем файла `liveletters.json` — техническое
  сообщение.

JSON передаётся как UTF-8, без base64url-кодирования. Технический JSON
намеренно вынесен во вложение, чтобы тело письма не выглядело как
обфусцированный блок текста для почтовых фильтров.

Получатель v1 разбирает письмо строго:

- корневое письмо должно быть `multipart/*`;
- среди непосредственных частей должна быть ровно одна `text/plain`;
- среди непосредственных частей должна быть ровно одна `application/json`,
  обозначенная как `liveletters.json` через `name` в `Content-Type` или
  `filename` в `Content-Disposition`;
- несколько человекочитаемых частей, несколько технических частей,
  техническая часть с другим именем и любые дополнительные части без
  манифеста отклоняются как неверный формат письма.

Вложения к записям и комментариям в v1 ещё не определены. Будущая версия
должна описывать каждую дополнительную MIME-часть в манифесте внутри
`liveletters.json`; до появления такого манифеста дополнительные части
запрещены.

Когда вложения появятся, защитные лимиты MIME нужно будет разделить:
отдельно ограничивать размер всего письма, размер `liveletters.json`,
число вложений, размер одного вложения и суммарный размер вложений. Простое
увеличение общего лимита письма без манифеста и отдельных лимитов не
считается поддержкой вложений.

Реализация также применяет защитные лимиты на размер сырого письма,
человекочитаемой части, `liveletters.json`, число MIME-частей и глубину
MIME-дерева. Письмо, вышедшее за эти лимиты, отклоняется до применения
события.

## JSON-сообщение

Вложение `liveletters.json` содержит объект:

```json
{
  "envelope": {
    "schema_version": "1",
    "event_type": "post_created",
    "resource_id": "alice@example.org",
    "event_id": "post-created-1712345678"
  },
  "origin": "Alice <alice@example.org>",
  "payload": {
    "kind": "post_created",
    "post_id": "post-1712345678",
    "resource_id": "alice@example.org",
    "created_at": 1712345678,
    "body": "Привет!",
    "body_format": "plain",
    "visibility": "public"
  }
}
```

В JSON нет поля с человекочитаемым телом. Человекочитаемый текст живёт в
MIME-части `text/plain`.

## `envelope`

`envelope` — технический конверт события.

| Поле | Тип | Обязательное | Смысл |
|---|---|---:|---|
| `schema_version` | string | да | Версия схемы JSON. Для v1 используется `"1"` |
| `event_type` | string | да | Тип события, например `post_created` |
| `resource_id` | string | да | Ресурс, к которому относится событие |
| `event_id` | string | да | Уникальный идентификатор события |

Все поля `envelope` должны быть непустыми после обрезки пробелов по краям.

Инварианты:

- `envelope.event_type` должен совпадать с `payload.kind`;
- `envelope.resource_id` должен совпадать с `payload.resource_id`;
- повторный `event_id` считается дубликатом и не применяется повторно.

## `origin` и `source`

`origin` — первичный источник события. Он присутствует всегда.

`source` — непосредственный источник доставки. Он необязателен. Если поля
`source` нет, получатель обязан считать `source == origin`.

Оба поля, если присутствуют, имеют строковый формат:

```text
Nickname <email@example.org>
```

Правила разбора:

- строка обрезается по краям;
- должен быть один адрес в угловых скобках;
- ник и адрес не могут быть пустыми;
- ник не может содержать `<` или `>`;
- адрес не может содержать `<` или `>`;
- адрес должен выглядеть как адрес электронной почты.

`origin` используется получателем для заполнения таблицы известных авторов.
Это не подписка и не отношение дружбы, а только факт: «этот автор встретился
в протокольном сообщении».

`source` не является автором события. Он нужен, когда письмо пришло не
напрямую от автора события.

Пример пересылки комментария:

1. Боб публикует запись.
2. Алиса комментирует запись Боба.
3. Боб рассылает комментарий своим подписчикам.
4. Ева получает письмо от Боба.

В письме Евы:

```json
{
  "origin": "Alice <alice@example.org>",
  "source": "Bob <bob@example.org>",
  "payload": {
    "kind": "comment_created"
  }
}
```

Ева сохраняет Алису как автора комментария. Боб в этом письме — только
непосредственный источник доставки.

## `payload`

`payload` — событие предметной области. Поле `kind` выбирает вариант
события. Имена событий в `kind` и `envelope.event_type` совпадают.

Общие правила:

- все `resource_id` должны быть непустыми;
- `created_at` — целое число, время события в секундах Unix;
- `body_format` принимает значения `plain`, `markdown`, `html`;
- `visibility` не может быть пустой строкой;
- сейчас используются уровни видимости `public` и `friends_only`.

### `post_created`

Создание записи.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `post_created` | да |
| `post_id` | string | да |
| `resource_id` | string | да |
| `created_at` | integer | да |
| `body` | string | да |
| `body_format` | string | да |
| `visibility` | string | да |

`body` не должен быть пустым после обрезки пробелов.

Пример:

```json
{
  "kind": "post_created",
  "post_id": "post-1712345678",
  "resource_id": "alice@example.org",
  "created_at": 1712345678,
  "body": "Привет!",
  "body_format": "plain",
  "visibility": "public"
}
```

### `comment_created`

Создание комментария.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `comment_created` | да |
| `comment_id` | string | да |
| `post_id` | string | да |
| `parent_comment_id` | string или null | да |
| `resource_id` | string | да |
| `created_at` | integer | да |
| `body` | string | да |
| `body_format` | string | да |
| `visibility` | string | да |

`resource_id` — ресурс исходной записи, а не обязательно автор
комментария. Комментарий наследует фактическую видимость исходной записи.
Если комментарий пересылает владелец исходной записи, `source` может
отличаться от `origin`.

### `post_hidden`

Скрытие записи.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `post_hidden` | да |
| `post_id` | string | да |
| `resource_id` | string | да |
| `created_at` | integer | да |

### `comment_edited`

Редактирование комментария.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `comment_edited` | да |
| `comment_id` | string | да |
| `post_id` | string | да |
| `resource_id` | string | да |
| `created_at` | integer | да |
| `body` | string | да |
| `visibility` | string | да |

`body` не должен быть пустым после обрезки пробелов.

### `subscription_requested`

Запрос подписки. Подписчик просит владельца ресурса присылать будущие
события ресурса.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `subscription_requested` | да |
| `resource_id` | string | да |
| `subscriber_delivery_address` | string | да |
| `created_at` | integer | да |

Ник и адрес подписчика передаются через `origin`. В payload нет отдельного
поля с ником подписчика.

### `subscription_confirmed`

Ответ владельца ресурса на запрос подписки.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `subscription_confirmed` | да |
| `resource_id` | string | да |
| `subscriber_delivery_address` | string | да |
| `accepted` | boolean | да |
| `created_at` | integer | да |

Если `accepted = true`, получатель переводит подписку из ожидания в
подтверждённые. Если `accepted = false`, ожидание удаляется.

### `subscription_revoked`

Отзыв подписки. Подтверждение не требуется.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `subscription_revoked` | да |
| `resource_id` | string | да |
| `subscriber_delivery_address` | string | да |
| `created_at` | integer | да |

### `friend_added`

Уведомление о добавлении в друзья.

| Поле | Тип | Обязательное |
|---|---|---:|
| `kind` | string = `friend_added` | да |
| `resource_id` | string | да |
| `friend_address` | string | да |
| `created_at` | integer | да |

Смысл события: ресурс из `origin` считает `friend_address` другом.
Получатель сохраняет у себя сведения «я в друзьях у этого ресурса».

Это событие не создаёт подписку и не рассылает старые записи. Записи
`friends_only` будут доставляться только тем получателям, которые
одновременно:

- подписаны на ресурс;
- есть в списке друзей владельца ресурса.

## Протокольные сценарии

Этот раздел описывает не форму отдельных сообщений, а ожидаемые
последовательности сообщений между участниками.

### Цикл подписки

Участники:

- Алиса — хочет читать ресурс Боба;
- Боб — владелец ресурса `bob@example.org`.

Шаги:

| Шаг | Кто отправляет | Кому | Событие | Что происходит у получателя |
|---:|---|---|---|---|
| 1 | Алиса | Боб | `subscription_requested` | Боб сохраняет Алису как подписчика своего ресурса |
| 2 | Боб | Алиса | `subscription_confirmed` | Алиса переводит подписку из ожидания в подтверждённые |

В `subscription_requested`:

- `origin` — Алиса;
- `resource_id` — ресурс Боба;
- `subscriber_delivery_address` — адрес, на который Алиса хочет получать
  письма.

В `subscription_confirmed`:

- `origin` — Боб;
- `resource_id` — ресурс Боба;
- `subscriber_delivery_address` — тот же адрес Алисы;
- `accepted = true`, если подписка принята.

Если Алиса повторно отправляет `subscription_requested` на тот же ресурс,
Боб должен вернуть содержательно такой же ответ: тот же ресурс, тот же
подписчик, тот же результат. Повторный запрос не должен создавать
дубликаты подписки.

Если письмо с запросом не доставлено и отправитель получает DSN-bounce,
ожидающая подписка может быть удалена локально.

### Отзыв подписки

Если Алиса больше не хочет получать ресурс Боба, она отправляет Бобу
`subscription_revoked`.

В `subscription_revoked`:

- `origin` — Алиса;
- `resource_id` — ресурс Боба;
- `subscriber_delivery_address` — адрес Алисы, который нужно убрать из
  подписчиков.

Боб удаляет подписчика. Отдельное подтверждение отзыва в v1 не требуется.

### Добавление в друзья

Дружба в LiveLetters означает право видеть записи `friends_only`. Это не
подписка в обратную сторону и не доставка старых записей.

Участники:

- Алиса — добавляет Боба в друзья;
- Боб — получает право видеть закрытые записи Алисы, если он подписан на
  Алису.

#### Алиса уже подписана на Боба

Шаги:

| Шаг | Кто отправляет | Кому | Событие | Что происходит у получателя |
|---:|---|---|---|---|
| 1 | Алиса | Боб | `friend_added` | Боб сохраняет, что Алиса считает его другом |

У Алисы локально появляется запись «ресурс Алисы → Боб в друзьях».

В `friend_added`:

- `origin` — Алиса;
- `resource_id` — ресурс Алисы;
- `friend_address` — адрес Боба.

#### Алиса ещё не подписана на Боба

В этом случае `lltt friend bob@example.org` сначала использует обычный цикл
подписки Алисы на Боба. В `subscription_requested` нет специального поля
`purpose` или другого признака «это запрос дружбы».

Шаги:

| Шаг | Кто отправляет | Кому | Событие | Что происходит |
|---:|---|---|---|---|
| 1 | Алиса | Боб | `subscription_requested` | Боб принимает обычный запрос подписки |
| 2 | Боб | Алиса | `subscription_confirmed` | Алиса завершает ожидающую подписку |
| 3 | Алиса | Боб | `friend_added` | Боб сохраняет, что Алиса считает его другом |

После шага 3:

- Алиса считает Боба другом;
- Боб знает, что он в друзьях у Алисы;
- Боб не становится подписчиком Алисы автоматически;
- Алиса не отправляет Бобу старые записи;
- будущие записи Алисы `friends_only` будут доставлены Бобу только если Боб
  подписан на Алису.

### Публикация записи

Когда владелец ресурса публикует запись, он создаёт `post_created`.

Для `visibility = public` запись рассылается подписчикам ресурса.

Для `visibility = friends_only` запись рассылается только пересечению:

```text
подписчики ресурса ∩ друзья владельца ресурса
```

Добавление в друзья без подписки не создаёт доставку. Подписка без дружбы
не даёт доступ к `friends_only`.

### Комментарий к чужой записи и пересылка

Участники:

- Боб — автор исходной записи и владелец ресурса;
- Алиса — комментирует запись Боба;
- Ева — подписана на Боба.

Шаги для публичной записи:

| Шаг | Кто отправляет | Кому | Событие | `origin` | `source` |
|---:|---|---|---|---|---|
| 1 | Алиса | Боб | `comment_created` | Алиса | отсутствует, значит Алиса |
| 2 | Боб | Ева | `comment_created` | Алиса | Боб |

В шаге 1 Алиса отправляет комментарий владельцу исходной записи. Боб
сохраняет комментарий у себя.

В шаге 2 Боб рассылает этот же комментарий подписчикам своего ресурса.
Первичным автором остаётся Алиса, поэтому у Евы `origin = Alice
<alice@example.org>`. Непосредственный источник доставки — Боб, поэтому
у Евы заполнен `source = Bob <bob@example.org>`.

Ева сохраняет Алису в известных авторах, но не подписывается на Алису.

### Комментарий к закрытой записи

Комментарий наследует фактическую аудиторию исходной записи.

Если исходная запись Боба имеет `visibility = friends_only`, то при
пересылке комментария Боб выбирает получателей так же, как для самой
записи:

```text
подписчики ресурса Боба ∩ друзья Боба
```

Если Алиса комментирует закрытую запись Боба, Алиса не решает, кому
рассылать комментарий. Она отправляет комментарий Бобу, а рассылку делает
Боб как владелец исходного ресурса.

Если Боб сам комментирует свою закрытую запись, комментарий также
рассылается только друзьям-подписчикам Боба.

Если комментарий является ответом на другой комментарий, аудитория всё
равно определяется исходной записью, а не родительским комментарием.

## Авторизация событий

В v1 авторство события определяется полем `origin`.

`source` не даёт права изменять чужие объекты. Он нужен только для
описания непосредственного отправителя письма.

Общие правила:

- запись создаёт автор из `origin`;
- комментарий создаёт автор из `origin`;
- изменения и скрытия проверяются по правам автора из `origin`;
- пересылка комментария может иметь `source != origin`, но автором
  комментария остаётся `origin`.

В v1 поле `origin` само по себе не является криптографическим
доказательством личности. См. раздел «Безопасность».

## Порядок доставки, дубликаты и отложенные события

Почта не гарантирует порядок доставки и может доставить письмо повторно.
Получатель должен быть готов к следующим ситуациям:

- пришло то же письмо с тем же `event_id`;
- пришло логически то же событие с новым `event_id`;
- комментарий пришёл раньше записи;
- подтверждение подписки пришло после повторного запроса;
- письмо не похоже на LiveLetters-сообщение.

Рекомендуемые исходы обработки:

| Исход | Когда используется |
|---|---|
| `malformed` | письмо не разбирается как нужный MIME или JSON |
| `invalid` | JSON разобран, но нарушены инварианты протокола |
| `duplicate` | `event_id` уже встречался |
| `replay` | событие новое по `event_id`, но его эффект уже применён |
| `deferred` | событие корректно, но пока не хватает зависимости |
| `unauthorized` | источник не имеет права применить событие |
| `filtered` | событие корректно, но не предназначено этой идентичности |
| `applied` | событие применено |

Отложенное событие должно храниться вместе с `origin`, чтобы повторная
обработка выполнялась от имени того же первичного источника.

## Рассылка

Способ выбора получателей не хранится внутри `liveletters.json`; он является
локальным решением отправителя и его исходящей очереди.

Сейчас используются три способа:

| Способ | Смысл |
|---|---|
| `Direct` | отправить конкретным адресам |
| `ResourceSubscribers` | отправить всем подписчикам ресурса |
| `ResourceFriends` | отправить подписчикам ресурса, которые есть в друзьях |

Публичные записи обычно рассылаются подписчикам ресурса. Записи
`friends_only` и комментарии к ним рассылаются только друзьям-подписчикам.

Если Алиса комментирует запись Боба, первичное событие создаёт Алиса, но
рассылку подписчикам записи делает Боб. Поэтому у подписчиков Боба может
быть `origin = Alice <alice@example.org>` и
`source = Bob <bob@example.org>`.

## Версионирование и расширяемость

Версия v1 обозначается двумя способами:

- заголовком письма `X-LiveLetters-Protocol: v1`;
- полем `envelope.schema_version = "1"` внутри JSON.

Получатель v1 должен отклонять сообщение, если не может разобрать JSON,
если не знает `payload.kind`, или если `envelope.event_type` не совпадает с
`payload.kind`.

Новые обязательные поля внутри существующего события требуют новой версии
протокола или явного правила совместимости. Новые необязательные поля
допустимы только если получатели старой версии могут безопасно их
игнорировать.

## Безопасность

LiveLetters v1 передаёт события через обычную электронную почту. Это
накладывает ограничения:

- `From` и `To` письма не являются доказательством личности;
- `origin` и `source` в JSON также не являются криптографическим
  доказательством;
- SMTP-серверы и почтовые клиенты могут менять служебные заголовки;
- письмо может быть доставлено повторно или позже других писем;
- приватность `friends_only` зависит от корректности локального списка
  друзей и подписчиков у отправителя.

В v1 нет цифровой подписи протокольного сообщения. Поэтому реализация
должна считать `origin` протокольным утверждением, а не доказанным фактом.
Будущая версия протокола может добавить подписи JSON-вложения или всего
MIME-сообщения.

Пароли, ключи и токены не должны попадать ни в человекочитаемую часть, ни в
`liveletters.json`.

## Полный пример

```text
From: alice@example.org
To: bob@example.org
Subject: =?utf-8?B?0J3QvtCy0LDRjyDQt9Cw0L/QuNGB0Yw=?=
X-LiveLetters-Protocol: v1
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="liveletters-boundary"

--liveletters-boundary
Content-Type: text/plain; charset="utf-8"

Алиса написала:

Привет, мир!
--liveletters-boundary
Content-Type: application/json; name="liveletters.json"
Content-Disposition: attachment; filename="liveletters.json"

{
  "envelope": {
    "schema_version": "1",
    "event_type": "post_created",
    "resource_id": "alice@example.org",
    "event_id": "event-1712345678"
  },
  "origin": "Alice <alice@example.org>",
  "payload": {
    "kind": "post_created",
    "post_id": "post-1712345678",
    "resource_id": "alice@example.org",
    "created_at": 1712345678,
    "body": "Привет, мир!",
    "body_format": "plain",
    "visibility": "public"
  }
}
--liveletters-boundary--
```

## Реестр литералов v1

### `event_type` / `payload.kind`

- `post_created`
- `comment_created`
- `post_hidden`
- `comment_edited`
- `subscription_requested`
- `subscription_confirmed`
- `subscription_revoked`
- `friend_added`

### `body_format`

- `plain`
- `markdown`
- `html`

### `visibility`

- `public`
- `friends_only`

### MIME

- протокольный заголовок: `X-LiveLetters-Protocol`
- значение версии в заголовке: `v1`
- тип контейнера: `multipart/mixed`
- человекочитаемая часть: ровно одна `text/plain; charset="utf-8"`
- техническая часть: ровно одна `application/json`
- имя технического вложения: `liveletters.json`
- дополнительные части: запрещены без манифеста вложений в
  `liveletters.json`
