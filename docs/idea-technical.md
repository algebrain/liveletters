# LiveLetters: техническое описание концепции

Документ описывает концепцию LiveLetters: локально-ориентированной блоговой и социальной системы в духе LiveJournal, где основным транспортом синхронизации служит электронная почта, а пользователь работает через самостоятельную CLI-утилиту `lltt` на Rust. Графический интерфейс в текущей версии не предусмотрен.

## Терминология

- **Доменное событие** — атомарный факт LiveLetters: создание поста, комментарий, изменение подписки, бан.
- **Протокольное сообщение** — `ProtocolMessage` в смысле крейта `liveletters-protocol`: конверт + читаемое тело + полезная нагрузка в формате JSON.
- **Внутреннее локальное событие** — событие клиента или локальной базы, которое не является частью межклиентского протокола и не требует доставки по электронной почте.
- **Ресурс** — блог, сообщество или иной логический канал публикации.
- **Идентичность** — именованная конфигурация аккаунта: почтовые адреса, подписки, владеемые ресурсы.
- **Домашний каталог LiveLetters** — `~/.liveletters/` либо значение переменной окружения `LIVELETTERS_HOME`.

## 1. Краткая формулировка

LiveLetters — локально-ориентированная блоговая и социальная система в духе LiveJournal, где основным транспортом синхронизации служит электронная почта, а пользователь работает через самостоятельную CLI-утилиту `lltt` на Rust. Графический интерфейс в этой версии не предусмотрен.

Система должна поддерживать:

- личные блоги;
- сообщества;
- посты и комментарии;
- древовидные обсуждения;
- подписки;
- список друзей;
- ограничение видимости записей;
- базовые социальные действия уровня классического ЖЖ.

## 2. Базовая архитектурная идея

Система не строится вокруг единого центрального сервера. У каждого ресурса есть владелец и собственный локальный источник истины.

Для каждого ресурса:

- владелец ресурса хранит каноническое состояние в локальной базе;
- клиент владельца формирует исходящие протокольные сообщения, несущие доменные события;
- подписчики и участники получают эти протокольные сообщения по электронной почте;
- на стороне подписчика локальный клиент строит локальную реплику состояния.

Иными словами:

- электронная почта нужна как транспорт доставки;
- локальная база владельца ресурса — канонический источник истины;
- локальные базы подписчиков — производные реплики.

## 3. Источник истины

Для личного блога источником истины является локальная база автора блога.

Для сообщества источником истины является локальная база владельца сообщества или выделенного управляющего узла сообщества.

Это означает:

- окончательная версия поста определяется у владельца ресурса;
- окончательная структура комментариев определяется у владельца ресурса;
- права доступа, членство, баны и модерационные решения определяются у владельца ресурса;
- входящие реакции и комментарии от других участников могут считаться предложенными изменениями до момента принятия и фиксации в канонической базе.

Такой подход упрощает модель конфликтов: система не обязана реализовывать полностью симметричную равноправную конвергенцию.

## 4. Роль электронной почты и IMAP

Электронная почта используется как транспорт протокольных сообщений, внутри которых передаются доменные события.

IMAP используется как удобный протокол доступа к хранилищу писем:

- для отправки и получения протокольных сообщений;
- для локальной индексации;
- для повторной синхронизации;
- для восстановления истории при переустановке клиента.

Это не «почтовый клиент с необычным интерфейсом», а прикладная система, использующая электронную почту как универсальный канал обмена.

На практике каждое протокольное сообщение LiveLetters, доставляемое по электронной почте, должно одновременно удовлетворять двум неотделимым требованиям:

- быть нормальным читаемым письмом, которое человек-получатель может открыть в любом почтовом клиенте и понять, что произошло, без помощи LiveLetters;
- нести техническую часть, пригодную для разбора клиентом LiveLetters.

Человекочитаемая часть не может быть пустой, формальной отпиской вроде «см. вложение» или иной заглушкой. Это содержательный текст письма — тот самый пост, комментарий или уведомление, которое увидел бы подписчик, не пользующийся LiveLetters. Техническая часть добавляется к этому письму, но не заменяет его.

Это правило действует именно для писем, доставляемых по электронной почте. Внутренние локальные события клиента, которые никуда не отправляются, не обязаны иметь человекочитаемое представление.

Техническая часть может передаваться:

- в теле письма отдельным машинно-читаемым блоком;
- во вложении в формате MIME;
- частично в заголовках вида `X-...`.

Рекомендуемый вариант для минимально рабочей версии:

- основная техническая полезная нагрузка — в отдельной MIME-части с JSON;
- минимальные данные о маршрутизации — в заголовках;
- человекочитаемый текст — в обычной текстовой части письма, той самой, которую показывает любой почтовый клиент.

Если письмо открывается во внешнем обычном почтовом клиенте, техническая часть может существовать в нём как скрытый или малозаметный слой, доступный только при желании пользователя. В самом LiveLetters техническая часть не обязана быть видимой вообще.

## 5. Модель доменных событий

Система должна быть событийно-управляемой, а не управляемой синхронизацией состояния.

То есть по почте желательно передавать не «всю текущую страницу блога», а протокольные сообщения, содержащие отдельные доменные события:

- создание поста;
- редактирование поста;
- удаление или скрытие поста;
- создание комментария;
- редактирование комментария;
- удаление комментария;
- изменение подписки;
- изменение дружбы;
- смена роли участника сообщества;
- бан;
- изменение настроек видимости.

Каждое доменное событие должно иметь как минимум:

- `event_id` — глобально уникальный идентификатор события;
- `event_type` — тип события;
- `resource_id` — идентификатор ресурса;
- `actor_id` — кто инициировал событие;
- `object_id` — идентификатор сущности, к которой относится событие;
- `created_at` — время создания события;
- `schema_version` — версия схемы;
- `parent_id` — при необходимости ссылка на родительскую сущность или событие;
- `payload` — полезная нагрузка доменного события.

Минимальная практичная модель:

- посты и комментарии имеют стабильные `object_id`;
- редактирование создаёт новое доменное событие, а не переписывает историю;
- клиент на стороне владельца ресурса сводит цепочку доменных событий к текущему состоянию;
- клиент подписчика делает то же самое на своей локальной реплике.

## 6. Идентичность и адресация

Нужно разделять как минимум четыре сущности:

- **идентичность аккаунта** — стабильный внутренний идентификатор;
- **ресурс** — блог или сообщество;
- **адрес доставки** — почтовый адрес, через который принимаются и отправляются сообщения;
- **имя конфига** — строка, под которой конфигурация идентичности лежит в `~/.liveletters/identities/`.

Один пользователь может иметь:

- несколько ресурсов;
- несколько почтовых адресов;
- отдельные адреса для чтения и публикации;
- несколько конфигов идентичностей на одной машине (например, разные личности в разных сообществах).

Из этого следует, что почтовый адрес не должен быть единственным идентификатором пользователя или ресурса.

Нужны устойчивые внутренние идентификаторы:

- `account_id`;
- `resource_id`;
- `post_id`;
- `comment_id`.

Почтовый адрес при этом остаётся транспортным адресом, а не главной сущностью доменной модели.

Конфигурация идентичности привязывает:

- ровно один `account_id`;
- один публикующий почтовый адрес;
- один или несколько принимающих почтовых адресов;
- произвольное число `resource_id`, которыми она владеет;
- список ресурсов, на которые она подписана, вместе с `delivery_address` каждого.

Переключение текущего пользователя liveletters в CLI: команда `lltt cu <имя>` записывает имя в файл `current-user` в домашнем каталоге; команда `lltt cu` без аргумента печатает имя текущего пользователя. По умолчанию используется конфиг `default`.

## 7. Публичность и приватность

В текущей концепции письма пересылаются без сквозного шифрования.

Это означает:

- система может ограничивать круг доставки;
- система может ограничивать круг отображения в клиенте;
- но система не гарантирует криптографическую конфиденциальность содержимого.

Следовательно, режимы:

- `public`;
- `friends_only`;
- `members_only`;
- `private_community`;

следует трактовать как правила доставки и отображения, а не как гарантию того, что содержимое недоступно почтовой инфраструктуре.

Корректная формулировка для документации: ограниченные режимы доступа определяют, кому система отправляет и показывает контент, но не обеспечивают криптографическую секретность самого письма.

Это приемлемо для минимально рабочей версии, если система не обещает больше, чем реально даёт.

## 8. Сообщества

Сообщество — это отдельный ресурс со своей локальной канонической базой и собственной политикой доступа.

Базовая модель сообщества:

- владелец;
- модераторы;
- участники;
- подписчики;
- забаненные пользователи.

Важно различать:

- право читать;
- право комментировать;
- право публиковать;
- право модерировать;
- право управлять составом участников.

В технической модели это означает отдельные типы доменных событий для:

- вступления и выхода;
- выдачи роли;
- отзыва роли;
- бана;
- разбана;
- публикации от имени сообщества;
- модерационного скрытия или удаления.

## 9. Комментарии и древовидные обсуждения

Древовидность должна быть явной частью модели данных.

У комментария должны быть:

- `comment_id`;
- `post_id`;
- `parent_comment_id` или `null` для корневого комментария;
- `author_id`;
- состояние видимости;
- временные метки создания и изменения.

При передаче по электронной почте протокольное сообщение должно явно содержать:

- к какому посту относится комментарий;
- к какому родительскому комментарию он прикреплён;
- в какой ресурс он публикуется.

Если этого не сделать, восстановление дерева по письмам будет ненадёжным.

## 10. Доставка, дубликаты и идемпотентность

Транспорт электронной почты ненадёжен в прикладном смысле:

- письма могут приходить с задержкой;
- письма могут дублироваться;
- порядок доставки не гарантирован;
- письмо может быть переслано повторно;
- клиент может импортировать историю несколько раз.

Поэтому обработка входящих протокольных сообщений и извлекаемых из них доменных событий должна быть идемпотентной.

Минимальные правила:

- каждый `event_id` обрабатывается один раз;
- повторное получение уже известного доменного события безопасно;
- доменные события можно применять вне порядка доставки, если хватает контекста;
- при нехватке контекста доменное событие кладётся в «отложенные» до появления зависимостей.

Например:

- комментарий может прийти раньше поста;
- редактирование может прийти раньше исходного создания;
- модерационное скрытие может прийти раньше копии исходного контента.

Значит, в клиенте нужен локальный индекс и очередь неполностью разрешённых доменных событий.

## 11. Локальная база

Для CLI-клиента разумно иметь локальную базу данных на диске, которая хранит:

- ресурсы;
- аккаунты;
- связи подписки и дружбы;
- посты;
- комментарии;
- роли и членство;
- журнал сырых протокольных сообщений и извлечённых событий;
- таблицу доставки и статусов обработки.

Практически полезно хранить отдельно:

- `raw_messages` — как протокольное сообщение пришло по почте;
- `raw_events` — какие доменные события из него были извлечены;
- `materialized_state` — текущее вычисленное состояние объектов.

Это даёт:

- переиндексацию;
- отладку;
- миграцию схемы;
- возможность чинить разборщик без потери истории.

## 12. Модель интерфейса

По интерфейсу CLI-утилита `lltt` — это самостоятельный инструмент для работы с LiveLetters, а не почтовый клиент.

Пользователь работает с командами вида:

- `lltt cu posts` — собственные посты текущего пользователя liveletters;
- `lltt feed` — лента подписок текущего пользователя liveletters;
- `lltt thread <id>` — тред поста;
- `lltt post new`, `lltt comment new` — публикация;
- `lltt sync` — полный цикл синхронизации;
- `lltt sync pull`, `lltt sync push` — отдельное получение и отправка;
- `lltt status`, `lltt doctor` — диагностика.

Транспорт электронной почты не должен диктовать пользовательский интерфейс и основную пользовательскую модель. В обычном выводе не показывается техническая полезная нагрузка, структура MIME или иные почтовые детали.

Отдельно может существовать диагностический режим, где можно:

- увидеть сырое письмо;
- увидеть техническую полезную нагрузку;
- понять, почему событие не применилось;
- при необходимости вручную переиндексировать письмо.

Такой режим нужен для разработки, диагностики и восстановления, но не является частью основной пользовательской модели.

Графический интерфейс в этой версии не предусмотрен. Он появится как отдельный слой поверх уже проверенной CLI-логики, после того как `lltt` закроет все ключевые сценарии end-to-end. Выбор UI-стека — отдельное решение, не относящееся к этому документу.

## 13. Предлагаемый минимально рабочий продукт

Чтобы не перегрузить первую версию, минимально рабочий продукт ограничивается CLI-утилитой `lltt` и базовыми сценариями.

Минимально рабочий продукт:

- CLI-утилита `lltt` на Rust;
- личные блоги;
- подписки;
- посты;
- комментарии;
- древовидные обсуждения;
- публичные записи и записи `friends_only`;
- локальная база на диске в `~/.liveletters/lltt.db`;
- несколько конфигов идентичностей в `~/.liveletters/identities/`;
- импорт протокольных сообщений из файла;
- полное скрытие технической части в обычном выводе.

Команда-индикатор готовности: `lltt feed` после импорта хотя бы одного протокольного сообщения из подписки возвращает непустую ленту подписок текущего пользователя liveletters.

Что лучше отложить:

- графический интерфейс;
- сообщества со сложной модерацией;
- лайки и реакции;
- баны;
- многоуровневые списки контроля доступа;
- настоящее сквозное шифрование;
- мобильный клиент;
- автоматическая сетевая синхронизация (тоже отложено: первая версия работает с импортом файлов).

## 14. Основные технические риски

1. **Стабильность схемы доменных событий и протокольных сообщений.** Если рано не зафиксировать понятный формат сообщений, потом будет сложно обеспечивать совместимость клиентов.
2. **Идентичность и доверие.** Если система полагается только на поле `From`, подделка отправителя станет серьёзной проблемой.
3. **Модерация и права.** Для сообществ быстро возникает необходимость в чётких правилах, какие доменные события считаются валидными и кто имеет право их выпускать.
4. **Конфликты и порядок доставки.** Нужно заранее проектировать систему как устойчивую к внеочередной доставке.
5. **Сложность CLI.** Если техническая составляющая слишком заметна, продукт начнёт ощущаться как «почтовый клиент для гиков», а не как блоговая платформа.
6. **Хрупкая зависимость `native-tls` в транспорте.** Задействована только при реальной сетевой работе; при импорте файлов не нужна. В плане — опциональная замена на `rustls`.

## 15. Что нужно формализовать следующим шагом

Следующий уровень детализации должен включать:

- схему идентификаторов;
- формат MIME-сообщения;
- JSON-схему для доменных событий;
- правила проверки доменного события;
- правила авторизации доменного события;
- таблицу состояний постов и комментариев;
- модель репликации;
- список инвариантов локальной базы;
- формат файлов конфигурации в `~/.liveletters/`;
- набор подкоманд `lltt` в виде объявления clap.

Подробный план работ по этим пунктам описан в `technical-plan.md`.

## 16. Обработка входящих писем и поведение при ответе и пересылке

В протокол нужно заранее заложить, что не каждое входящее письмо является валидным протокольным сообщением и не каждое протокольное сообщение несёт применимое доменное событие.

Любое входящее письмо должно сначала рассматриваться как кандидат на разбор, а не как готовое доменное действие.

Рекомендуемая последовательность обработки:

1. Получить сырое письмо и сохранить его в локальном журнале.
2. Определить, похоже ли письмо на сообщение LiveLetters.
3. Если да, извлечь техническую полезную нагрузку.
4. Проверить целостность, схему и обязательные поля.
5. Проверить, не является ли доменное событие дубликатом или повторным воспроизведением старого события.
6. Проверить, имеет ли отправитель право выпускать такое доменное событие для данного ресурса.
7. Только после этого применять доменное событие к локальному состоянию.

Из этого следует, что нужно различать несколько сущностей:

- транспортное письмо;
- техническая полезная нагрузка;
- доменное событие;
- пользовательский текст письма.

Они могут находиться внутри одного почтового сообщения, но не должны смешиваться на уровне протокольной логики.

### Ответ на письмо

Обычный ответ из внешнего почтового клиента не должен автоматически считаться комментарием или иным прикладным действием.

Причины:

- почтовый клиент может изменить структуру MIME;
- полезная нагрузка может быть процитирована частично или целиком;
- письмо может содержать только свободный текст без корректной структуры;
- заголовки могут быть изменены или потеряны;
- адрес ответа может не совпадать с ожидаемым маршрутом публикации.

Рекомендуемое правило:

- обычный ответ не меняет состояние ресурса сам по себе;
- он становится комментарием только если содержит валидное протокольное сообщение с корректным доменным событием и проходит проверку прав;
- в противном случае он трактуется как обычное письмо или как невалидная попытка действия.

### Пересылка письма

Обычная пересылка не должна считаться новым доменным событием по умолчанию.

Пересланное письмо может содержать копию старой полезной нагрузки, но такая копия не должна повторно применяться как новое изменение состояния.

Рекомендуемое правило:

- пересылка никогда не считается новым прикладным действием только по факту пересылки;
- пересланное письмо может быть сохранено как транспортный артефакт;
- старая полезная нагрузка внутри пересылки должна распознаваться как уже существующее или неавторизованное доменное событие, а не как новый факт доменной модели.

### Классификация входящих писем

После разбора письмо полезно относить к одной из категорий:

- `valid_event`;
- `duplicate_event`;
- `replayed_event`;
- `unauthorized_event`;
- `malformed_event`;
- `plain_email`;
- `unknown_transport_artifact`.

Это даёт:

- предсказуемую обработку;
- понятную диагностику;
- возможность ручного разбора спорных случаев;
- защиту от «угадывания» намерений пользователя по слабым сигналам.

### Идемпотентность и защита от повторного воспроизведения

Протокол должен быть устойчив к повторной доставке и повторному воспроизведению старых писем.

Минимально нужны:

- глобально уникальный `event_id`;
- хранение уже обработанных `event_id`;
- проверка, не применялось ли доменное событие ранее;
- связь между доменным событием и его автором;
- возможность отклонять доменное событие, если оно пришло в недопустимом контексте.

Если система позже придёт к криптографическим подписям, они должны использоваться не только для идентификации автора, но и для защиты от подмены и частичного переписывания полезной нагрузки.

### Консервативное поведение клиента

LiveLetters должен вести себя консервативно:

- если письмо не прошло строгую проверку, оно не должно менять состояние ресурса;
- если письмо похоже на ответ или пересылку, но не содержит корректного доменного события, его нужно считать обычным письмом;
- если письмо содержит корректную полезную нагрузку, но отправитель не имеет прав, доменное событие должно быть отклонено;
- если случай неоднозначен, письмо лучше отправить в диагностическую или карантинную категорию, чем пытаться автоматически интерпретировать его смысл.

Общая политика может быть зафиксирована так:

- только структурированное и валидное сообщение LiveLetters может менять состояние ресурса;
- обычные действия внешнего почтового клиента сами по себе не являются прикладными действиями LiveLetters;
- транспортное письмо и доменное событие связаны, но не тождественны.

## 17. Структура крейтов

Этот раздел фиксирует обоснование выбранной структуры кодовой базы.

### 17.1. Решения по разбиению

Кодовая база делится на десять библиотечных крейтов и одно приложение. Границы проведены по реальным осям ответственности, а не по удобству каталога.

**Группы крейтов по ответственности:**

- **Чистая доменная модель.** `liveletters-domain` — сущности, события, идентификаторы, без зависимостей. Это нижняя точка графа; все остальные крейты опираются на неё.
- **Формат сообщений.** `liveletters-protocol` — сериализация и конверт протокольного сообщения, единственная зависимость — `serde`.
- **Криптография секретов.** `liveletters-secret-box` — XChaCha-Poly1305, жизненный цикл файла ключа, обфускация и деобфускация. Ортогонально хранению: пригодится и для будущих нереляционных секретов.
- **Разбор форматов.** `liveletters-mime` — чистый разбор и сборка MIME без сетевого ввода-вывода, без зависимости от `native-tls`.
- **Работа с локальной БД.** `liveletters-store` — SQLite, схемы, миграции, разрешение путей в домашнем каталоге.
- **Конфигурация на диске.** `liveletters-config` — формат TOML в `~/.liveletters/`, разбор конфигов идентичностей, маппинг между форматом на диске и рабочими структурами `liveletters-app-core`. Отдельный крейт, потому что on-disk-формат и runtime-структуры имеют разный жизненный цикл миграций.
- **Сетевые транспорты.** `liveletters-mail` — IMAP и SMTP, конфигурация и статусы. Единственный крейт, где нужна хрупкая зависимость `native-tls`; транспорты выделены за признаком `network`, по умолчанию выключенным.
- **Прикладная логика разбора.** `liveletters-sync` — разбор входящих протокольных сообщений и применение доменных событий с идемпотентностью и отложенной обработкой.
- **Прикладной сервис.** `liveletters-app-core` — команды, запросы, рабочие модели, фасад `AppCore`. То, что должен звать CLI.
- **Наблюдаемость.** `liveletters-diagnostics` — снимки состояния и здоровья поверх стора.

**Решения, которые были бы соблазнительны, но отвергнуты:**

- Делить `liveletters-app-core` на «команды» и «запросы» — они слишком связаны через фасад, выгода от разделения меньше цены абстракций.
- Делить `liveletters-mail` на отдельные крейты IMAP и SMTP — у них общие конфигурационные типы и параллельные транспорты, держать вместе компактнее.
- Выделять `liveletters-store-paths` в отдельный крейт — файл маленький, чистый, без зависимостей; отдельный крейт избыточен.

### 17.2. Решения по работе с внешним миром

Подделки данных в оперативной памяти в проекте не используются. Это сознательное решение, зафиксированное в трёх правилах.

**Правило 1: локальная БД всегда на диске.** Конструктор `Store::open_in_memory` отсутствует. `Store` всегда открывается по пути на диске. В юнит-тестах — через `tempfile::TempDir` и `Store::open_for_home_dir(temp_home)`.

**Правило 2: сетевые транспорты реальные.** В `liveletters-mail` нет «in-memory» вариантов транспорта. Все сетевые тесты используют локальный SMTP/IMAP сервер (mailpit, Greenmail или аналог), запускаемый в среде тестирования.

**Правило 3: разбор и применение событий тестируются через временный каталог.** Юнит-тесты логики разбора и применения событий (`liveletters-sync`, `liveletters-app-core`) конструируют `ReceivedEmail` и `OutgoingEmail` напрямую и работают с реальной БД через временный каталог. Транспортный интерфейс в эти тесты не вовлекается.

Эти правила обеспечивают равенство среды разработки, тестов и реальной работы: один и тот же путь кода, одна и та же схема БД, один и тот же код разбора MIME. Расхождения между тестами и реальностью не маскируются подделками, а явно проявляются.

### 17.3. Карта крейтов

```
modules/
  liveletters-domain/         # сущности, события, идентификаторы
  liveletters-protocol/       # формат сообщений и конверты
  liveletters-secret-box/     # XChaCha-Poly1305, файл ключа
  liveletters-mime/           # разбор и сборка MIME без ввода-вывода
  liveletters-mail/           # транспорты IMAP и SMTP, конфигурация
  liveletters-store/          # SQLite, схемы, миграции, пути
  liveletters-config/         # TOML-формат, разбор конфигов
  liveletters-sync/           # разбор входящих, применение событий
  liveletters-app-core/       # команды, запросы, рабочие модели
  liveletters-diagnostics/    # снимки состояния и здоровья

apps/
  lltt/                       # CLI-утилита
```

Каталог верхнего уровня содержит: `Cargo.toml` рабочего пространства, `docs/` с публичной документацией, десять каталогов под `modules/` и `apps/`.

### 17.4. Граф зависимостей

```
domain ──▶ protocol ──▶ mime ──▶ mail
              │                       │
              │                       ▼
              │                    store
              │                       ▲
              │                       │
              │                  secret-box
              │                       ▲
              │                       │
              │                    config ──▶ app-core
              │                       ▲       │
              │                       │       │
              │                    diagnostics
              │                       ▲
              └───────────────────────┘
                                      │
                                   sync
                                      │
                                   lltt
```

Слои:

- **Уровень 0** — `liveletters-domain`: чистые типы, ноль зависимостей.
- **Уровень 1** — `liveletters-protocol`, `liveletters-secret-box`: сериализация и криптография, изолированно.
- **Уровень 2** — `liveletters-mime`, `liveletters-store`: разбор форматов и работа с БД.
- **Уровень 3** — `liveletters-mail`, `liveletters-config`: транспорты и конфигурация.
- **Уровень 4** — `liveletters-sync`, `liveletters-app-core`, `liveletters-diagnostics`: прикладная логика.
- **Уровень 5** — `apps/lltt`: единственная точка входа для пользователя.

## 18. Домашний каталог `~/.liveletters/`

Все пользовательские артефакты лежат в одном каталоге. Никаких глобальных путей в коде.

```
~/.liveletters/
├── config.toml                       # общие настройки, не привязанные к идентичности
├── identities/                       # альтернативные конфиги идентичностей
│   ├── default.toml
│   ├── alice.toml
│   └── bob.toml
├── current-user                      # имя текущей идентичности (одна строка, без расширения)
├── lltt.db                           # основная SQLite-база
├── inbox/                            # каталог для импорта входящих (mbox/файлы)
├── outbox-staged/                    # подготовленные, но не отправленные письма
├── logs/
└── mail-password-obfuscation.key     # ключ обфускации секретов
```

Поведение при инициализации (`lltt init`):

1. Создаёт каталоги `identities/`, `inbox/`, `outbox-staged/`, `logs/`.
2. Создаёт файл `lltt.db` через `Store::open_for_home_dir` и прогоняет миграции.
3. Создаёт `mail-password-obfuscation.key` с правами `0o600` на Unix-системах.
4. Создаёт минимальный `config.toml` и `identities/default.toml`.
5. Создаёт файл `current-user` со значением `default`.
6. Не предпринимает сетевых действий.

Поведение при выборе домашнего каталога:

- если установлена переменная окружения `LIVELETTERS_HOME`, используется её значение;
- иначе используется `~/.liveletters/`.

Поведение при выборе текущей идентичности:

- текущая идентичность хранится в файле `current-user` в домашнем каталоге;
- команда `lltt cu <имя>` записывает имя в этот файл и печатает подтверждение;
- команда `lltt cu` без аргумента печатает текущее имя (если файл отсутствует, печатает `default`).

Глобальных флагов для выбора домашнего каталога, идентичности или формата вывода в CLI нет. Формат вывода всегда человекочитаемый; если потребуется машиночитаемое представление, оно будет добавлено отдельной задачей.

## 19. Методология разработки

При работе над проектом соблюдаются правила из `~/.codex/AGENTS.md`:

1. Сначала красный тест, потом код, потом зелёный — везде, где это осмысленно.
2. Изменения документации — только после того, как соответствующие тесты зелёные.
3. Русскоязычная документация пишется чистым русским языком, без англицизмов, где возможно.
4. Исходные файлы держатся в пределах 600 строк; при превышении — разбиваются на файлы с тематическими названиями. Тесты выносятся в отдельные файлы.
5. План работ и внутренние проектные документы хранятся в локальных каталогах (не публикуются в репозитории). Публичная документация ведётся в `docs/`.
6. В публичной документации не используются абсолютные ссылки; только относительные.
7. В корне проекта ведётся `.gitignore` с разумным содержимым: локальные каталоги для заметок и планов разработчика, `*.local`, `*.local.*`, `target/`, `Cargo.lock` для бинарей-приложений (для библиотек — `Cargo.lock` коммитится).
